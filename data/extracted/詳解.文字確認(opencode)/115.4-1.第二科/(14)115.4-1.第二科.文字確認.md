## 題目（來源：考卷 PDF 第 3–4 頁）

某企業導入大型語言模型（LLM）分析內部報表，使用者經常提供 Excel 匯出的表格資料（如銷售數據與統計表）。測試時發現，模型對原始表格解析效果不穩定。為提升模型理解與回應品質，下列哪一種上下文工程（Context Engineering）作法較為適當？

(A) 將表格內容轉換為結構化 JSON 或 Markdown table；
(B) 在維持原始表格呈現方式下，補充欄位與數據說明；
(C) 將表格資料隨機切割後分段輸入；
(D) 直接提供原始表格內容以保留完整資訊

**官方答案：A（將表格內容轉換為結構化 JSON 或 Markdown table）**

## 1. 場景與關鍵字（上方）

- 場景：LLM 分析內部 Excel 報表時，對**原始表格解析不穩定**；問哪種 Context Engineering 作法能提升理解與回應品質。
- 關鍵字：**Context Engineering**、表格序列化（serialization）、JSON／Markdown table、結構化輸入、DataFrame.to_markdown／to_json、LLM 表格推理、欄位與值對齊。

## 2. 逐項判定（綠框依據）

| 選項 | 判定 | 理由 |
|---|---|---|
| A 將表格內容轉換為結構化 JSON 或 Markdown table | **最正確** | LLM 的輸入本質是 token 序列；把表格轉成有明確欄位名稱與值的結構化文字（JSON／Markdown 表格）能降低解析歧異，讓模型穩定對齊「欄位↔數值」。pandas `DataFrame.to_markdown()`／`to_json()` 正是常見的序列化工具；此屬上下文工程在「輸入呈現形式」上的標準處置。 |
| B 維持原始表格呈現方式，補充欄位與數據說明 | ❌ 錯誤 | 補充說明是好事，但「維持原始呈現方式」保留了造成解析不穩定的根因（合併儲存格、對齊混亂、空白欄等）；不是最適當的首要作法。 |
| C 將表格資料隨機切割後分段輸入 | ❌ 錯誤 | 「隨機」切割會破壞表格的欄位對應關係，讓資料更難解讀；不同於第 13 題有語意依據的 Chunking。 |
| D 直接提供原始表格內容以保留完整資訊 | ❌ 錯誤 | 題幹已明言原始表格解析不穩定；直接提供等於不處理問題。「保留完整資訊」不能補償解析失敗。 |

## 3. 錯置選項（紅框）與未來選答規則

- B 是**補說明但留病根**：萬用加分項，但未處理格式。
- C 是**偽 Chunking**：第 13 題的切分有語意依據，本題「隨機」切表只會錯位。
- D 是**不改進錯置**：把「保留原文」當成品質保證。
- 未來選答規則：
  1. 看到「LLM＋表格解析不穩」→ 先想 **轉成 JSON／Markdown table 等結構化文字**。
  2. 看到「隨機切割」→ 直接排除；有效切分必須保留語意／欄位關係。
  3. 看到「維持原始呈現／直接提供」→ 若題幹已說原始格式有問題，就是錯項。
- 誠實補充：本命題以「結構化序列化優於原始表格」為考點；實務上亦需搭配清楚的欄位定義與適度表格大小，單靠格式轉換不是萬靈丹。
