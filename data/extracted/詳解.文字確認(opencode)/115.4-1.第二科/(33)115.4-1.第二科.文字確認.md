## 題目（來源：考卷 PDF 第 7–8 頁）

某醫療院所希望改善行政效率，規劃讓各科室人員可自行建立行政回報與內部申請表單，並導入 AI 功能以自動判讀與分類填寫內容（如問題類型或需求性質），同時需兼顧流程調整彈性與降低系統開發維運負擔。下列哪一種技術組合最適合？

(A) Low-Code 平台 × 預訓練語言模型 API；
(B) No-Code 平台 × 規則式自動化（Rule-based Automation）；
(C) 傳統程式開發 × 自建深度學習模型；
(D) 試算表工具 × 手動資料標記分析

**官方答案：A（Low-Code 平台 × 預訓練語言模型 API）**

## 1. 場景與關鍵字（上方）

- 場景：醫療院所讓**各科室人員自行建立表單**，並要**自動判讀／分類**填寫內容（問題類型、需求性質）；限制是「**流程調整彈性**」與「**降低開發維運負擔**」要同時滿足。
- 關鍵字： citizen developer（市民開發者）、Low-Code、No-Code、預訓練語言模型 API、文件處理／分類、規則式自動化、自建深度學習、維運負擔。

## 2. 逐項判定（綠框依據）

| 選項 | 判定 | 理由 |
|---|---|---|
| A Low-Code × 預訓練語言模型 API | **最正確** | Low-Code 讓科室在可控框架下自行調表單與流程（Gartner：加速應用開發與維護；Microsoft Power Platform：low-code tools 建立 app 與 workflow）；預訓練語言模型 API 提供自然語言判讀與分類能力，不必自建模型，正好降低維運負擔。Microsoft 官方文件亦區分：Azure OpenAI 供開發者以 API 整合進階 AI，AI Builder 供 citizen developers 做表單／文件處理。 |
| B No-Code × 規則式自動化 | ❌ 錯誤 | 規則式自動化依賴固定 if-then 條件，難以處理「問題類型／需求性質」這類自由文字的語意分類；且 No-Code 在流程調整彈性上通常低於 Low-Code，不符合題目「兼顧彈性」的要求。 |
| C 傳統程式開發 × 自建深度學習模型 | ❌ 錯誤 | 自建模型需要資料標註、訓練、部署與監控，與「降低系統開發維運負擔」直接衝突；也不利各科室自行調整表單。 |
| D 試算表 × 手動資料標記分析 | ❌ 錯誤 | 手動標記不是 AI 自動判讀／分類，完全未滿足「導入 AI 功能」的需求。 |

## 3. 錯置選項（紅框）與未來選答規則

- B 是**能力錯配**：規則式 Automation 適合結構化固定流程，不適合語意分類；No-Code 也較難兼顧客製彈性。
- C 是**成本錯配**：自建深度學習模型把維運負擔推到最高。
- D 是**自動化錯置**：手動標記等於沒有導入 AI。
- 未來選答規則：
  1. 看到「非技術人員自建表單／流程」→ Low-Code／No-Code；
  2. 再加「需要判讀自由文字、自動分類」→ 優先**預訓練語言模型 API**；
  3. 同時要求「彈性＋低維運」→ 避開自建模型與純規則式；
  4. 看到「手動」字樣而題目要求 AI → 直接排除。
