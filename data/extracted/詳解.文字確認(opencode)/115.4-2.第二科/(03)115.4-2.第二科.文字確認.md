## 題目（來源：考卷 PDF 第 1 頁）

某人資部門使用 Dify 平台建立了一個 AI 面試輔助機器人，協助 HR 在面試過程中即時查詢應徵者的過往提問紀錄。然而測試時發現，機器人完全無法記住同一位應徵者在五分鐘前說過的話，每次回應都像是全新對話。以下哪個措施能從根本上解決此問題？

(A)提升語言模型的溫度參數（Temperature）；
(B)在每次 API 請求中，手動將歷史對話內容（Chat History）一併打包送入模型進行推理；
(C)改用具備更多參數的大型多模態模型，以強化跨輪對話的理解能力；
(D)為伺服器增加記憶體容量，擴充系統可儲存的對話快取空間

**官方答案：B（在每次 API 請求中手動將歷史對話內容（Chat History）一併打包送入模型）**

## 1. 場景與關鍵字（上方）

- 場景：人資部門以 Dify 建立 AI 面試輔助機器人；實測發現模型不記得五分鐘前同一應徵者說過的話，每次回應都像全新對話，需找出「根本解決」多輪記憶的措施。
- 關鍵字：**聊天記錄（Chat History）**、**API 無狀態（stateless）**、多輪對話、上下文管理、Temperature、模型參數規模、伺服器快取

## 2. 逐項判定（綠框依據）

| 選項 | 判定 | 理由 |
|---|---|---|
| A 提升 Temperature | ❌ 錯 | Temperature 控制回應的隨機性與多樣性，與是否攜帶先前對話無關；提高只會讓回覆更不穩定。 |
| B 手動打包 Chat History | **最正確（正解）** | OpenAI 官方文件明確指出每次文字生成請求都是獨立且無狀態的；要實現多輪對話，必須在請求中提供先前的訊息。 |
| C 換更大或多模態模型 | ❌ 錯 | 參數規模或多模態能力不改變 API 無狀態的本質；模型再大也不會自動得知未被送入的對話。 |
| D 增加伺服器記憶體 | ❌ 錯 | 伺服器快取不是模型上下文；若請求本身未帶入歷史對話，模型仍看不到先前內容。 |

## 3. 錯置選項（紅框）與未來選答規則

- A、C、D 分別把問題誤歸因於「隨機性」「模型能力」「硬體記憶體」，但真正的瓶頸是**請求層級沒有帶入歷史訊息**。
- 易混淆點：有些平台或框架會「自動」維護 conversation state，但底層仍是把歷史訊息放入請求；題目問「從根本上」，正解就是明確打包 Chat History。
- 未來選答規則：看到「模型不記得上一輪說什麼」，先想到 stateless API ＋ 傳入 prior messages，而不是調溫度或加記憶體。
