## 題目（來源：考卷 PDF 第 3 頁）

某家企業希望開發股票交易輔助工具，要求該工具需要在接收到市場報價資料的 50 毫秒內完成訊號判斷與下單指令，且每秒需處理超過一萬筆高併發交易。若選用 Low-Code 平台開發，最難克服的先天限制為何？

(A)Low-Code 平台無法串接任何金融市場的外部 API，因此無法獲取即時報價資料；
(B)Low-Code 平台無法串接任何券商平台的下單 API，因此無法進行即時交易；
(C)Low-Code 底層封裝通用框架，在毫秒級延遲與超高吞吐量（Throughput）的極限效能場景中，難以進行深度底層優化；
(D)Low-Code 平台無法建立即時更新的使用者介面，無法顯示動態報價資訊

**官方答案：C（Low-Code 底層封裝通用框架，在毫秒級延遲與超高吞吐量場景難以深度底層優化）**

## 1. 場景與關鍵字（上方）

- 場景：股票交易輔助工具要求 50 毫秒內完成判斷與下單、每秒超過一萬筆高併發；題目問選用 Low-Code 時最難克服的「先天限制」。
- 關鍵字：**低延遲（50 毫秒）**、**高吞吐量（每秒萬筆）**、底層封裝與抽象化、深度效能優化、API 串接誤區、極限效能場景

## 2. 逐項判定（綠框依據）

| 選項 | 判定 | 理由 |
|---|---|---|
| A 無法串接市場 API | ❌ 錯 | Low-Code 平台通常具備連接器與 API 串接能力（見第 6 題來源）；「無法串接任何」是絕對化錯誤。 |
| B 無法串接下單 API | ❌ 錯 | 同上，串接能力不是先天限制；問題在於延遲與吞吐量，而非能不能連。 |
| C 底層封裝難以深度優化 | **最正確（正解）** | 低碼平台以預建元件與抽象層換取開發速度； IBM 與 Wikipedia 的低碼說明皆以「最少手寫程式、視覺化元件」為核心，意味開發者難以改寫底層以追求極限效能。 |
| D 無法建立即時更新介面 | ❌ 錯 | 低碼平台可做儀錶板與即時更新介面；且題目瓶頸在交易路徑，不在 UI。 |

## 3. 錯置選項（紅框）與未來選答規則

- A、B、D 都把「不一定做不到」說成「無法」，與低碼平台的連接器／UI 能力不符，也沒有回答「先天限制」。
- **查證限制**：公開文件多描述低碼的抽象化與開發速度，未直接給出「50 毫秒／每秒萬筆」的量化門檻；此處是就抽象化本質推論，量化判斷建議人工覆核。
- 未來選答規則：看到「毫秒級、超高併發、極限效能」＋「低碼」，首選「底層封裝、難以深度優化」；不要被「無法串接」的絕對句誤導。
