# 專案共用資源

## 專案用途

這是一個協助準備「AI 應用規劃師」歷屆考題的專案。

目前目標：

1. 管理歷屆試題。
2. 支援依年份、科目、單元、關鍵字搜尋題目。
3. 記錄作答與錯因。
4. 依單元統計正確率。
5. 後續可加入 OCR 匯入與模擬考試。

## 共用資料位置

所有工具都應使用同一個專案根目錄：

```text
C:\Users\User\Documents\備考專案檔案夾
```

目錄用途：

```text
備考專案檔案夾/
├─ AGENTS.md             # 所有代理工具的共同工作規則
├─ src/                  # 應用程式程式碼
├─ data/
│  ├─ originals/         # 原始歷屆考題 PDF、照片或掃描檔
│  └─ extracted/         # OCR 文本、清理後題目與衍生資料
└─ docs/                 # 共用說明、決策與對話紀錄
```

## 資料規則

- `originals/` 中的原始檔案為唯讀；不得修改、移動、重新命名、刪除或覆寫。
- `data/originals/` 內所有檔案（含使用者放入的代理名稱資料夾）都是唯讀基準，**不得移動、修改、覆寫、新增或刪除**。凡是要放進 `data/originals/` 的內容，都必須先經**人工覆核**後才由使用者放入；代理只產出在生成區，不自行放進 originals。
- **筆記本 Gemini 的角色（2026-11-26 使用者澄清）**：它是 NotebookLM 筆記本 `ipas.動態回饋分析模式` 內的助手，**不是代理**，只處理筆記本內的事務；代理不須等它回覆。115.4-1 第一科 opencode 試做可行後，使用者才決定直接做「詳解.文字確認」，因此 OpenCode 以 originals 考卷與公開事實查證獨立完成 100 題，各題「Gemini 並列比較」標為「不適用」，不聲稱比對過任何 PNG。
- **繁體中文要求（2026-11-26 使用者指示）**：讀者大部分使用繁體中文，所有文字確認產出**必須全繁體、不可有簡體字**。OpenCode 已完成檔案以 OpenCC `s2tw` 逐字自查（保護繁體正字白名單：台／里／系／后／准／制／干／音／于／采／吃／床／群／秘），115.4-2／115.4-3 中斷時殘留的 680 個簡體字已修正。子代理完成每批後亦須做同樣自查，確認零簡體字才算完成。
- **人工核准與兩條產線定位（2026-11-26 使用者澄清）**：人工核准是「放入 `data/originals/`」的**前置作業**，不是 OpenCode／Antigravity 產線 commit 的前置；兩條產線可自主完成並 commit，不用擔心核准阻塞。OpenCode（`詳解.文字確認`）角色是**再次確認**，若與人工初核或其他來源不同，如實並行記錄、不互相覆寫；Antigravity（`詳解.圖解`）目的在讓讀者更好理解情境，每張圖右下角都有來源依據與證明（全部文件都有）。兩條產線平行獨立。
- 生成區專屬工作區：`data/extracted/詳解.文字確認(opencode)/<題組>/` 與 `data/extracted/詳解/<題組>/antigravity/` 分別是 OpenCode 與 Antigravity 的專屬可寫區；只有所屬代理能寫入自己的資料夾，其他代理不得代改。所有生成產出都放在 `data/extracted/`，不放在 `data/originals/`。
- `data/originals/考情資料整理/`（含 `統計分析/`）內的統計圖表與分析素材由使用者自行調整維護；代理只讀取比對，不修改、移動或重新產生，發現問題只回報。
- OCR 和文字清理結果放在 `extracted/`。
- 每份衍生資料應保留來源檔名、頁碼或來源資訊。
- 數學公式、圖表、特殊符號若 OCR 有誤，應人工標記並修正。
- 未經確認前，不得把 `originals/` 中的資料視為轉換完成或答案正確。

## 第一版實作

- 前端採用純 HTML、CSS 與 JavaScript；PDF 匯入使用 Python 與 `pypdf`，依賴列於 `requirements.txt`。
- `src/index.html` 是本機試題與練習入口；以瀏覽器開啟即可依關鍵字、年份及科目練習，並瀏覽原始 PDF。
- 目前已放入 10 份 PDF，涵蓋 114 年第 4-4 次及 115 年第 4-1 至 4-4 次、兩個考試科目；原始考卷集中存放於 `data/originals/歷屆考題/`，皆為唯讀基準。
- 使用 `pypdf` 從 PDF 文字層匯入 400 道選擇題（目前尚未包含 115 年第 4-4 次）。`src/extract_pdfs.py` 產生逐頁原始文字，`src/build_question_bank.py` 解析答案、選項並輸出 `data/extracted/questions.js`。115 年第 4-4 次兩科已由使用者置入，OpenCode 唯讀驗證結果為各科 50 題、題號 1–50 連續、答案與四選項齊全；重新匯入前須先讓擷取器指向 `歷屆考題/` 資料夾，否則會找不到根目錄 PDF，匯入後題庫預計為 500 題。
- 每題保留原始檔名及頁碼；網頁練習可即時核對答案並跳回來源頁。匯入器會檢查題號連續及四個選項齊全，但結構檢查不等同人工逐題校對。
- 官方學習指引及勘誤表放在 `data/originals/學習指引/`；指引是學習參考，不是正式教材或題庫，考試範圍以官方簡章公告為準。參考資料及核驗狀態見 `docs/官方學習資源索引.md`。
- 作答核對結果與錯因筆記會保存在目前瀏覽器的 `localStorage`，每題只保留最近一次答案、對錯、核對時間及筆記；錯題可重做，已訂正題目只要保留筆記仍可檢視。清除瀏覽器網站資料會一併清除紀錄，資料不會跨瀏覽器或裝置同步。
- 學習統計顯示整體、依年份及依科目的已核對數、答對數與正確率，計算依據是每題最近一次核對結果；目前尚無單元正確率統計，部分題目已可查看詳解圖（見下）。任何題目疑義以 `data/originals/` 的原始 PDF 為準。
- 題庫另含場景分類：`data/extracted/scenario_classification.json` 記錄 400 題的人工檢視結果，其中 327 題有標籤，73 題已檢視但暫無適用場景；場景標籤依題幹實際情境、多選。這是專案初步分類，不代表官方考綱。
- 練習區可依場景篩選，也可分別選擇「未分類（已檢視）」與「尚未檢視」題目；場景統計不計入未分類題目，且一題可能有多個標籤，各場景題數與作答數不可直接相加視為整體總數。調整分類時先更新 `scenario_classification.json`，再執行題庫建置器。
- 115.4-2 第一科、115.4-2 第二科、115.4-3 第一科及 115.4-3 第二科的詳解 PNG 已建立題號索引：`explanations.json` 對應原始檔案，練習頁核對答案後可開啟詳解圖；詳解圖片未 OCR 成文字，原始檔案也未修改。詳解圖片有增減時，先執行 `python src\build_explanation_index.py` 重建索引。
- **隱私決策**：原始詳解圖片與版面模板僅供本機使用，已由 `.gitignore` 排除，不推送到公開 repo。`explanations.json` 只記錄路徑，不含圖片內容；對外發布的重繪解說圖另行存放於 `data/extracted/diagrams/`。任何代理都不得移除這條忽略規則或直接 push 圖片。

重新匯入題目時，在專案根目錄執行：

```powershell
python -m pip install -r requirements.txt
python src\extract_pdfs.py
python src\build_explanation_index.py
python src\build_question_bank.py
```

## 跨工具協作方式

在 Herdr 中建立或開啟此專案時，讓 OpenCode、Antigravity 與其他代理都以此資料夾為工作區。

任何對專案結構、技術選擇或資料格式的重要決策，都要更新：

- 專案規則：`AGENTS.md`
- 專案說明與決策：`docs/專案共用資源.md`

這樣即使對話分開、工具重新啟動或切換代理，共用資源仍可從檔案中讀取。

**獨立平行作業**：Antigravity 與 OpenCode 各自獨立作業、互不等待對方交接。OpenCode 負責詳解文字追認與溯源，產出放在 `data/extracted/詳解.文字確認(opencode)/<題組>/`；Antigravity 負責詳解圖解、渲染與自驗，產出放在 `data/extracted/詳解/<題組>/antigravity/`。`data/originals/` 內檔案不得移動或新增；發現對方產出有問題時只記錄並回報，不代改；人工最終核准仍為提交前必要門檻。

## 三方共用溝通機制（機制 1）

為了讓 Copilot、Antigravity、OpenCode 都能快速知道各流程階段的工作與使用者意圖，並在發生狀況時即時支援，共用紀錄放在 `docs/代理溝通/`：

```text
docs/代理溝通/
├─ 00_現況與需求.md   # 使用者需求、流程階段狀態、異常與支援需求
├─ copilot.md         # Copilot 對話與工作摘要
├─ antigravity.md     # Antigravity 對話與工作摘要
├─ opencode.md        # OpenCode 對話與工作摘要，含視覺驗證回報格式
└─ 最新動態.md        # 由腳本自動產生的濃縮摘要（請勿手動編輯）
```

讀寫規則：

1. 任何代理開始工作前，先讀取 `00_現況與需求.md` 與三份代理紀錄。
2. 每次對話或任務結束後，由所屬代理在自己的檔案寫入：日期、使用者需求、結論／決定、異動檔案、待辦／需支援事項。
3. 若影響流程階段、使用者需求或產生異常，同步更新 `00_現況與需求.md`。
4. 發現問題只回報負責代理，不自行代改他人產物。
5. 此機制為共用檔案記錄；代理必須主動讀取才能取得其他代理的進度。
6. 自動化工具（已授權使用）：
   - 寫入紀錄：`powershell -File scripts\add-agent-log.ps1 -Agent copilot -Title "標題" -UserRequest "需求" -Conclusion "結論" -ChangedFiles "檔案" -FollowUp "待辦"`（Agent 也可為 `antigravity`、`opencode`）。
   - 更新摘要：`powershell -File scripts\watch-agent-logs.ps1 -Once`（只更新一次）。
   - 持續監聽：`powershell -File scripts\watch-agent-logs.ps1`（四份來源檔有異動時自動重產 `最新動態.md`，Ctrl+C 結束）。

原有的 `docs/對話紀錄.md` 保留作為歷史對話紀錄，不因本機制移動或改寫。

## 共用比對基準（三方通用）

OpenCode、Antigravity、Copilot 三方都可讀取並對照 Antigravity 的產出與 `data/originals/` 內的基準；`data/originals/` 內所有檔案全數唯讀，任何檔案都不得移動、新增、修改、覆寫或移出。兩代理的專屬可寫工作區在生成區 `data/extracted/詳解.文字確認(opencode)/<題組>/` 與 `.../antigravity/`，且各代理只能寫入自己的資料夾。

基準及其關係：

- `data/originals/整理建構問題框架..docx`（區域 1）：**由使用者提出問題、定義框架**的文件，不是 Notebook Gemini 產生的。
- 筆記本 `ipas.動態回饋分析模式`（NotebookLM）：其 sources 由使用者手動整理後放入 `data/originals/`；三方都可查閱，作為框架背後的資料依據。
- `data/originals/詳解/` 內的 PNG：Notebook Gemini **依上述框架與 sources 產出**的詳解圖，由使用者放入，是視覺依據。
- 原始 PDF：題目、選項與官方答案的依據。
- Antigravity 放置在 `src/` 的可重現版面，應同時符合框架文字、筆記本 sources、詳解圖視覺規格，以及原始 PDF 的題目與答案。

三方比對時，須理解「使用者問題框架（區域 1）→ 筆記本 ipas.動態回饋分析模式 sources → Gemini 詳解 PNG 圖面各位置 → Antigravity 版面」的對應關係；框架項目與圖面位置的明細對照目前只記錄原則，不自行推測，以避免三方認知不同。

### 框架 ↔ 圖面位置示範（3代理需知範例）

`data/originals/3代理需知範例/` 是三方共用的「框架項目 ↔ 圖面位置」範例，內含：

- `範例.docx`：框架的文字內容（對應區域 1 的提問方式）
- `(25)115.4-1.第一科.png`：依框架完成的圖面範例

對照規則：

| 框架項目 | 圖面位置 | 內容性質 |
|---|---|---|
| 1. 場景（標示關鍵字） | 上方 | 搜尋整理的準確內容 |
| 2. 為何選項錯誤（B/C/D，標示關鍵字） | 第二欄上下綠紅框 | 搜尋整理的準確內容 |
| 3. 網路比對後說明場景差異、色框內理由、未來如何選答案 | 色框內 | 搜尋整理的準確內容 |
| 4. 套用 `115.4-1.(08)` 標準版面 | 全圖：Col 2 上下綠紅框、其餘單一高框、文字換列不重疊、箭頭準確 | 版面標準 |
| 5. 簡介**發明者（年份）與設計目的** | **右下角** | **來源依據** |
| 5. 題目設計目的／動機與關鍵字 | 中下角 | 搜尋整理的準確內容 |
| 5. 初級題號標示 + 適中級／初級範圍評估與理由 | 左下角 | 搜尋整理的準確內容 |

重點：**右下角就是來源依據**（發明者、年份、設計目的）；其他區塊都是搜尋整理出來的準確內容。三方做比對時，依此範例判斷「哪一塊該在哪裡、属于什麼性質」，避免認知不同。

此資料夾屬於 `data/originals/`，同樣唯讀，不可移動、修改或覆寫。

### 版面改版原則（目的優先）

原始詳解圖有兩個刻意設計的區域，改版可調方向、排列或呈現方式，**只要目的保留即不算偏離**：

| 區域 | 原始做法 | 必須保留的目的 |
|---|---|---|
| 上方階段步驟 | 水平橫幅 | 讓流程順序一眼明確 |
| 右手反饋迴路圖 | 垂直 | 呈現情境（回饋的來回過程） |

視覺驗證檢查的是「目的是否達成」，不是「形式是否跟原圖一樣」。上方換了排列但步驟仍清楚、右手換了形狀但情境仍在，都算合格；反之，形式一樣但看不出步驟或情境，才算偏離。

### 全部詳解圖交叉對照（三方通用）

`data/originals/詳解/` 共有 **210 張 Notebook Gemini 詳解 PNG**，分四個題組：115.4-2 第一科 52 張、115.4-2 第二科 50 張、115.4-3 第一科 57 張、115.4-3 第二科 51 張。

三方都可對照**所有**詳解圖的位置配置。這些圖彼此之間**高比例位置一致**，因此任一張都可作為位置配置的交叉基準：

- 上方：場景（標示關鍵字）
- 第二欄上下綠紅框：何處選項錯誤的理由
- 色框內：網路比對說明、理由與未來如何選答案
- 全圖：`115.4-1.(08)` 標準版面，箭頭準確、文字不重疊
- **右下角：來源依據（發明者、年份、設計目的）**
- 中下角：題目設計目的／動機與關鍵字
- 左下角：題號與初級／適中級範圍評估

右下角以外都是搜尋整理的準確內容。全部檔案唯讀，不可移動、修改或覆寫。目前模型不能讀圖，逐張交叉比對需換成支援圖片的模型。

### 角色界線：文字追認與視覺驗證分開

- OpenCode 只做**文字內容確認與溯源**，不做渲染後視覺驗證；目前模型 `opencode/big-pickle` 也不能讀圖。若必須從圖片取文字，改用支援圖片輸入的模型（如 `opencode/nemotron-3.5-super-vl-free`）或請 Antigravity 提供文字。
- 渲染後視覺驗證（換行、重疊、箭頭端點、GitHub Pages 實際版面）由 **Antigravity** 在自己的 `antigravity/` 工作區完成；人工最終核准仍為第二道防線。
- 回報差異時須註明使用的驗證方式，且只回報給負責代理，不代改其產物。

### 題組狀態（三方皆須知道）

- `115.4-1 第一科`、`115.4-1 第二科` 已由使用者放入 `data/originals/詳解/` 做唯讀對照基準；兩代理的生成產出分别放在 `data/extracted/詳解.文字確認(opencode)/<題組>/` 與 `.../antigravity/`。題組仍屬部分完成（第一科 PNG 1–42、文字確認 41–50；第二科 PNG 1–30、HTML 31–50）。
- 桌面殘留檔案不是專案基準，代理不得移動、複製或提前引用。
- 115 年第 4-4 次第一科、第二科考卷已公布並由使用者置入 `data/originals/歷屆考題/`，已成為唯讀基準。

`data/originals/詳解/` 內所有 PNG 都是使用者放入的基準檔，只能讀取比對。發現差異依「只回報、不代改」處理，回報給 Antigravity 修正後再驗證。

## 詳解圖工作指派

詳解圖依下列流程分工：

```text
Notebook Gemini（產生結構化內容）
  -> 存入 data/originals/
  -> 人工確認題目、答案與事實來源
  -> 兩條獨立平行產線（互不等待交接）：
       OpenCode   ：文字追認與溯源 -> data/extracted/詳解.文字確認(opencode)/<題組>/
       Antigravity：圖解、渲染與自驗 -> data/extracted/詳解/<題組>/antigravity/
  -> 人工最終核准
```

### Antigravity

- 將已由人工初核的結構化內容轉成可重現的 HTML、CSS 或 SVG。
- 批量產生 PNG，不應讓文字直接由一般圖像生成模型繪製，以降低字形、換行與框線重疊風險。
